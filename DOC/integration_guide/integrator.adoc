[[aou-ig-module-overview]]
== 1. Module Overview

[[aou-ig-aou_top]]
=== 1.1 AOU_TOP

[.monospaced]#++AOU_TOP++# is the recommended top-level integration module. It
instantiates two submodules:

* *[.monospaced]#++AOU_FDI_BRINGUP_CTRL++#* -- A UCIe 3.0 FDI state machine that manages
the four FDI handshake pairs (wake, clock, state negotiation, RX
activation) required to bring the FDI link from RESET to ACTIVE and
follow LinkError, LinkReset, Disabled, Retrain, and L1 entry/exit.
* *[.monospaced]#++AOU_CORE_TOP++#* -- The AXI-over-UCIe protocol engine described in
xref:aou-ig-aou_core_top[Section 1.2].

The bringup controller drives [.monospaced]#++I_INT_FSM_IN_ACTIVE++# into the protocol
engine internally, so this signal is not exposed as a top-level port on
[.monospaced]#++AOU_TOP++#. Instead, [.monospaced]#++AOU_TOP++# exposes:

* FDI bringup control ports for the physical layer handshakes
(xref:aou-ig-fdi-bringup-control-interface-aou_top-only[Section 3.14])
* Software bringup control pins
(xref:aou-ig-fdi-bringup-software-control-aou_top-only[Section 3.15])
* Bringup status outputs
(xref:aou-ig-fdi-bringup-status-aou_top-only[Section 3.16])

The FDI bringup flow is described in
xref:aou-ig-fdi-bringup-flow-aou_top-only[Section 6.6].

[[aou-ig-purpose-and-function]]
==== 1.2.1 Purpose and Function

The AOU_CORE_TOP is a bridge between AXI interface and the UCIe FDI
interface, defined in AoU standard, AXI over UCIe Protocol Specification
v0.7.

To achieve low latency, AOU_CORE directly handles signals related to the
UCIe FDI interface data flow control and processes data in FDI-width
chunks (32, 64, or 128 bytes, as selected by the [.monospaced]#++FDI_CONFIG++# parameter)
in a cut-through manner, without converting them to 256-byte flit data.
It receives AXI messages from its own AXI slave interface, packs them
into FDI-width chunks, and transmits these chunks to the remote AoU
device via UCIe. The remote AoU receives these FDI-width chunks from the
UCIe FDI interface, unpacks them into AXI messages, and delivers the
data through its AXI master interface. It supports flow control for all
exceptional cases defined in the UCIe standard. First, it handles the
chunk valid/cancel signal, including the alternative implementation
method described in the UCIe specification. Second, it handles the stall
request signal received from the D2D Adapter while maintaining the
Flit-aligned boundary.

Interoperability is also supported when the remote device uses a
different AXI data width. AOU_CORE supports a configurable number of
Resource Plane(RPs), with both the number of RPs and each RP’s AXI data
width fully parameterizable. A dedicated field in the SFR allows
software to configure the target RP, enabling flexible RP mapping. The
AW and AR channels are arbitrated between RPs with one of three schemes:
Round Robin, AXI QoS, and Port QoS; W data follows the order of the
granted AWs. Additionally, a starvation-prevention mechanism is
implemented to ensure fair arbitration across all RPs.

AOU_CORE_TOP implements the subset of FDI signals required specifically
for transporting AXI across UCIe. FDI bringup/teardown and FDI sideband
flows are expected to be handled by other components.

The block consists of the following sub blocks

* AOU_CORE
** AOU_CORE_RP Manages a AXI interface for write request, read request,
write data, read data and write response busses
** AOU_CORE_SFR This implements control and status register of the AOU
core. It has a 32bit APB interface for programming. It configures all
the blocks in the core.
** AOU_TX_CORE This block packs the arbitrated AXI channels, credits,
and activation messages into FDI-width chunks (32, 64, or 128 bytes per
[.monospaced]#++FDI_CONFIG++#). It follows AOU specifications to pack the messages into
256 byte flit data. It then passes it onto UCIe controller over the FDI
interface for transmission.
** AOU_CRD_CTRL This block manages credits available for TX. It gets
remote credits available from AOU_RX_CORE, and used credits from
AOU_TX_CORE and creates final credits that can be used for TX.
** AOU_RX_CORE This block processes FDI-width chunks (32, 64, or 128
bytes per [.monospaced]#++FDI_CONFIG++#) received by UCIe controller and passed to the
core over the FDI interface. It decodes different message types which
encapsulate different AXI channel transactions. These messages are
buffered and then passed onto AOU_CORE_RP for presenting the transaction
to its corresponding AXI interface.
** AOU_TX_FDI_IF This block receives FDI-width data chunks from
AOU_TX_CORE and buffers them. It does handshake with UCIe controller FDI
RX interface and passes the data chunks downstream to be sent to remote
chiplet.
** AOU_ACT_CTRL This block manages activation and deactivation control
of the AOU bridge. It initiates activate and deactivate messages to
remote AOU bridge when configured via APB.
* AOU_FIFO_RP This block buffers decoded messages from AOU_RX_CORE. It
separates the messages based on resource plane (RP) indicator and writes
them into dedicated FIFOs. These FIFOs feed the corresponding
AOU_CORE_RP which manage a single AXI interface. The FIFOs are on the
core reset together with AOU_CORE (I_RESETN and AOU_CON0.AOU_SW_RESET,
xref:aou-ig-reset-domains[Section 3.1.1]).
* ASYNC_APB_BRIDGE This block synchronizes APB transactions to the local
core clock.

When using [.monospaced]#++AOU_CORE_TOP++# directly, the integrator must provide an
external FDI state machine that drives [.monospaced]#++I_INT_FSM_IN_ACTIVE++# and the
associated control/status signals listed in
xref:aou-ig-ucie-external-control-and-status[Section 3.12].

[[aou-ig-key-features]]
==== 1.2.2 Key Features

* Single APB interface Configuration/control/status register access
* Multiple AXI master & slave interface
** Configurable RP port & RP remapping supported
** Supports variable data widths and burst length requests. Configurable
FIFO Depth
* UCIe 256B latency-optimized flit(Format 6) support only
* Message packing and unpacking are handled in variable-sized units of
32, 64, or 128 bytes, corresponding to the FDI data width selected by
[.monospaced]#++FDI_CONFIG++#.
* Selectable Early response by setting SFR8
* Selectable 32B / 64B / 128B single-PHY and 32B+64B / 64B+128B two-PHY
FDI configurations via the [.monospaced]#++FDI_CONFIG++# parameter (see
xref:aou-ig-parameter-list[Section 2]). Two-PHY variants additionally
require the [.monospaced]#pass:c[+define+TWO_PHY]# build flag so the second-PHY ports
physically exist.
* Parameterized number of Resource Plane and each RP’s AXI data width
* RP Remapping
* QoS scheme between RPs on the AW and AR channels
* Interoperability with different data width remote die
* Handling of flit cancel and stall request as specified in the UCIe
specification
* Selectable AXI Aggregator added for BUS efficiency

[[aou-ig-reset-domains]]
==== 3.1.1 Reset domains

[.monospaced]#++I_RESETN++# and [.monospaced]#++I_PRESETN++# are independent.
Each may be asserted or released on its own.

[.monospaced]#++I_RESETN++# is the core-clock reset. It returns the protocol
engine, the configuration registers, and the activation state to their
reset values. The activation FSM comes out of reset
[.monospaced]#++DISABLED++#. It clears the RX FIFOs. On
[.monospaced]#++AOU_TOP++#, it returns the FDI bringup controller to Reset,
so the link must be trained again. In-flight AXI transactions and an FDI
flit already in progress are abandoned. Software reprograms the
configuration registers, brings the link up, and runs activation again.
[.monospaced]#++AOU_SW_RESET++# is the software reset used in the LinkReset
sequence
(xref:../MAS/software-operation.adoc#aou-736-pm-entry--linkreset--linkdisabled-sequence[Section 7.3.6]).
It resets AOU_CORE the same way, the AXI port logic and the RX FIFOs
(AOU_FIFO_RP) of every RP included, with no quiesce or drain; every
configuration register returns to its reset value, the
[.monospaced]#++AOU_SW_RESET++# bit itself included, so the bit is
write-only and self-clearing and the reset lasts one
[.monospaced]#++I_CLK++# cycle. Scan muxing of that path is described in
xref:aou-ig-tiel_dft_modescan-usage[Section 3.13.1].

*AXI transactions across a reset.* Either reset loses every AXI
transaction in flight or queued in AOU_CORE: requests accepted on the S
ports and not yet sent, bursts in progress on the S or M ports, responses
owed to the local managers (for reads and writes already sent to the
remote die too), responses the local subordinates present on the M ports,
and writes already acknowledged with an early write response whose data has
not reached the remote die. Nothing is completed with an error response, and
the ports do not keep the AXI protocol across the reset: VALID can drop
without a handshake, a burst can end early, a response presented to an M
port is never accepted and a response owed on an S port never comes. The
integrator must therefore either reset the AXI managers and subordinates
attached to the AoU ports together with AOU_CORE (the same reset event; on
[.monospaced]#++AOU_CORE_TOP++#, [.monospaced]#++O_SW_RESET++# reports the
software reset, xref:aou-ig-ucie-external-control-and-status[Section 3.12]),
or give them a recovery mechanism that abandons the transactions
outstanding towards AOU_CORE, withdraws what they present and ignores a late
response. Nothing a reset lost is presented on a port after it: the RX
FIFOs are emptied with the core, so no beat or response received before the
reset is delivered later, and the activation that follows advertises the
full FIFO depth as credit. Software restarts the lost traffic once AOU_CORE
is activated again. Only the LinkReset sequence resets with traffic pending;
the PM entry and LinkDisable sequences drain it first (Section 7.3.6).

[.monospaced]#++I_PRESETN++# is the APB-clock reset. It resets only the
APB-clock side of the asynchronous APB bridge. Configuration, activation
state, AXI traffic, and the FDI link stay as they are. Assert
[.monospaced]#++I_PRESETN++# or [.monospaced]#++I_RESETN++# only after the
APB master is idle ([.monospaced]#++PSEL++# low, with no access waiting on
[.monospaced]#++PREADY++#) and the bridge's request/done handshake has fully
returned to idle in both clock domains. Keep both clocks running and
[.monospaced]#++PSEL++# low while allowing the handshake to drain before an
independent reset; master-visible completion alone is insufficient.
A write still sitting in the bridge can complete after the reset and
change a register that the reset just cleared.

At power-on, hold both resets asserted while [.monospaced]#++I_CLK++# and
[.monospaced]#++I_PCLK++# are running. Start APB or AXI traffic only after
both resets have been released.

(offsets 0x0000 to 0x0080) repeats at every 64 KiB within the APB window.
Size the APB window for 64 KiB and let the interconnect decode the upper
address bits. Within the window, an offset that is not a defined register
(including a non-word-aligned address) reads as 0x00000000 and ignores
writes. [.monospaced]#++PREADY++# is tied high and
[.monospaced]#++PSLVERR++# is tied low, so every access completes in one
cycle without an error, mapped or not. The interface has no
[.monospaced]#++PSTRB++#; writes are 32 bits wide.

* [.monospaced]#++I_INT_FSM_IN_ACTIVE++# is an input signal that indicates that the

lost (LinkError, LinkReset, Disabled, or Reset); AOU_CORE treats every
falling edge while its activation FSM is not DISABLED as a link loss,
returns the FSM to DISABLED and raises [.monospaced]#++INT_FDI_LINK_DOWN++#, so a
controller that drops it on every Retrain gives software that interrupt on
every Retrain. This is what [.monospaced]#++AOU_FDI_BRINGUP_CTRL++#'s

remote die has been answered) is tracked inside AOU_CORE and reported in
[.monospaced]#++AOU_INIT.SLV_TR_COMPLETE++# / [.monospaced]#++AOU_INIT.MST_TR_COMPLETE++#; no external

responses of writes that received an early B response
([.monospaced]#++WRITE_EARLY_RESPONSE_RPn.WRITE_RESP_DONE++#).

DISABLED, allowing the UCIe link to go down. Once deactivation
completes, [.monospaced]#++O_AOU_ACTIVATE_ST_DISABLED++# is asserted to notify the
UCIE_CORE.
* When the AOU_CORE is in the ENABLED state, [.monospaced]#++O_AOU_ACTIVATE_ST_ENABLED++#
is asserted to notify the UCIE_CORE.
* [.monospaced]#++O_AOU_REQ_LINKRESET++# is asserted together with
[.monospaced]#++INT_REQ_LINKRESET++# when the AOU_CORE detects an AoU protocol
violation, to notify the UCIE_CORE. It is a level: the sticky
[.monospaced]#++LP_LINKRESET++# status bits through their interrupt masks, held
until software clears the status, and absent for a masked cause.
[.monospaced]#++AOU_FDI_BRINGUP_CTRL++# acts on it in ACTIVE and RETRAIN; raised while
the link is in L1 or exiting it, the request is deferred until the link is next
Active (xref:aou-ig-supported-state-transitions[Section 6.6.3]).

[.monospaced]#++AOU_CON0.AOU_SW_RESET++# holds AOU_CORE in reset. An external FDI
state machine should use it the way [.monospaced]#++AOU_FDI_BRINGUP_CTRL++# does
(xref:aou-ig-supported-state-transitions[Section 6.6.3]): after a LinkError,
AOU_CORE's FDI data paths keep the position of the flit the LinkError
interrupted until this reset, so the link must not return to Active before
it has been applied.

[[aou-ig-tiel_dft_modescan-usage]]
==== 3.13.1 TIEL_DFT_MODESCAN Usage

[.monospaced]#++TIEL_DFT_MODESCAN++# controls a glitch-free mux ([.monospaced]#++u_sw_reset_mux++#,
instance of [.monospaced]#++AOU_SOC_GFMUX_LVT++#) that selects the reset source for
[.monospaced]#++AOU_CORE++#:

....
                          TIEL_DFT_MODESCAN
                                |
                              I_SEL
                         +-------------+
  ~r_sw_reset & I_RESETN |  I_A        |
  (functional SW reset)  |   GFMUX     |---> w_DFTED_sw_resetn ---> AOU_CORE.I_RESETN,
                         |             |                            AOU_FIFO_RP.I_RESETN
                         |  I_B        |
  AOU_SOC_BUF(1'b1)     |             |
  (scan bypass: high)    +-------------+
....

* *Functional mode* ([.monospaced]#++TIEL_DFT_MODESCAN++# = 0): The mux selects [.monospaced]#++I_A++#,
the functional software-controlled reset path
([.monospaced]#++~r_sw_reset & I_RESETN++#). This allows the CSR-writable SW reset to
combine with the hardware reset.
* *Scan mode* ([.monospaced]#++TIEL_DFT_MODESCAN++# = 1): The mux selects [.monospaced]#++I_B++#, a
constant [.monospaced]#++1'b1++# driven through [.monospaced]#++AOU_SOC_BUF++#
([.monospaced]#++dft_persistent_buf_scan_resetn_sw++#). This value de-asserts the
active-low SW reset, neutralizing it so that scan chains can shift
freely without the software reset logic interfering with controllability
or observability. [.monospaced]#++AOU_CORE++# and [.monospaced]#++AOU_FIFO_RP++# stay out of
reset for as long as [.monospaced]#++TIEL_DFT_MODESCAN++# is high, in shift and in capture. A
write to [.monospaced]#++AOU_SW_RESET++# in scan mode does not reset them: the bit stays set
and [.monospaced]#++O_SW_RESET++# stays high until [.monospaced]#++TIEL_DFT_MODESCAN++# falls,
and the software reset then takes effect.

The [.monospaced]#++AOU_SOC_BUF++# instance exists solely to prevent the synthesis tool
from optimizing away the tied-high constant; it must be preserved as a
persistent buffer (see xref:aou-ig-library-cell-replacement[Section 8.7]).

The SDC file ([.monospaced]#++INTEG/constraints/aou_core_top.sdc++#) constrains this pin
with [.monospaced]#++set_case_analysis 0++# in functional timing mode.

[[aou-ig-integrator-dft-responsibilities]]
==== 3.13.2 Integrator DFT Responsibilities

The design provides internal DFT muxing only for the software-controlled
reset path ([.monospaced]#++w_DFTED_sw_resetn++#). The two primary hardware resets and
all scan infrastructure are the integratorpass:[']s responsibility:

[width="100%",cols="<50%,<50%",options="header",]
|=======================================================================
|Responsibility |Detail
|*HW reset DFT muxes* |[.monospaced]#++I_RESETN++# and [.monospaced]#++I_PRESETN++# have no internal
scan-mode bypass. The integrator must add external DFT muxes (or
equivalent) on both resets so they can be held inactive (high) during
scan shift and capture. Without this, all flip-flops using these resets
will be uncontrollable during ATPG.

[[aou-ig-interrupts]]
== 5. Interrupts

* *INT_ACTIVATE_START* An interrupt that occurs when activation of the
AoU Protocol layer is required. The interrupt can be cleared by writing
pass:[']1pass:['] to the AOU_CORE.AOU_INIT.INT_ACTIVATE_START SFR.
* *INT_DEACTIVATE_START* An interrupt that occurs when deactivation of
the AoU Protocol layer is required. The interrupt can be cleared by
writing pass:[']1pass:['] to the AOU_CORE.AOU_INIT.INT_DEACTIVATE_START SFR.
* *INT_SI0_ID_MISMATCH* An interrupt that occurs on the AXI Slave
Interface when a B or R channel response is received with an ID that was
not previously issued as a request. Each RP's checker is enabled by
AOU_CORE.AXI_SLV_ID_MISMATCH_ERR_RPn.AXI_SLV_ID_MISMATCH_EN. Program that
bit only while the activation FSM is DISABLED and no AXI traffic is
outstanding on that RP. SW can check the mismatched AXI ID by reading
AOU_CORE.AXI_SLV_ID_MISMATCH_ERR_RPn. The interrupt can be cleared by
writing pass:[']1pass:['] to AXI_SLV_BID_MISMATCH_ERR or
AXI_SLV_RID_MISMATCH_ERR.
* *INT_MI0_ID_MISMATCH* An interrupt that occurs on the AXI Master
Interface when a B or R channel response is received with an ID that was
not previously issued as a request. SW can check the mismatched AXI ID
by reading AOU_CORE.ERROR_INFO SFR. The interrupt can be cleared by
writing pass:[']1pass:['] to the AOU_CORE.ERROR_INFO.SPLIT_B/RID_MISMATCH_ERR SFR.
* *INT_EARLY_RESP_ERR* An interrupt that occurs when, due to the Write
Early Response feature, a B response has already been sent through the
AXI Slave Interface, and a subsequent actual B response arrives with an
Error. SW can check the ID and error type of the transaction in which
the error occurred by reading AOU_CORE.WRITE_EARLY_RESPONSE SFR. The
interrupt can be cleared by writing pass:[']1pass:['] to the
AOU_CORE.WRITE_EARLY_RESPONSE.WRITE_RESP_ERR SFR.
* *INT_EARLY_WDT_ERR* An interrupt that occurs when the write-transaction
watchdog of an RP expires: with AOU_CORE.WRITE_EARLY_RESPONSE_RPn.WDT_EN
set, no AW or B handshake occurred for
AOU_CORE.WRITE_EARLY_RESPONSE_WDT_CTL.WDT_THRESHOLD I_CLK cycles (reset
0xC3500) while the RP had writes outstanding, typically because the
remote die stopped answering writes that already received an early
OKAY. SW can find the RP by reading
AOU_CORE.WRITE_EARLY_RESPONSE_RPn.WDT_TRANS_TIMEOUT_ERR; the interrupt is
cleared by writing pass:[']1pass:['] to that bit and masked with
AOU_CORE.AOU_INTERRUPT_MASK.INT_EARLY_WDT_MASK (bit 9). The watchdog of an
RP fires once per reset: after a timeout it does not re-arm until I_RESETN or
AOU_CON0.AOU_SW_RESET. See
[.monospaced]#++DOC/MAS/software-operation.adoc++# section 7.2.6 for the recovery
sequence.
* *INT_REQ_LINKRESET* An interrupt that occurs when AOU_CORE receives a
protocol violation. Refer to the _AOU_CORE Micro-Architecture
Specification_ ([.monospaced]#++DOC/MAS/interrupts-errors.adoc++#) for debugging details.
When AOU_CORE receives a protocol violation, SW needs to do SW reset
AOU_CORE and re-enter the activation sequence.
* *INT_FDI_LINK_DOWN* An interrupt that occurs when the FDI link is lost
while AoU is in use: [.monospaced]#++I_INT_FSM_IN_ACTIVE++# falls (on
[.monospaced]#++AOU_TOP++#, the bringup FSM left ACTIVE for LINKERROR, LINKDOWN or
RESET; Retrain and L1 do not count) while the activation FSM is in
ACTIVATE, ENABLED or DEACTIVATE. The activation FSM returns to DISABLED in
the same cycle and drops any handshake in flight, so no Ack timeout
follows. The status bit is AOU_CORE.AOU_INIT.INT_FDI_LINK_DOWN (bit 12,
write pass:[']1pass:['] to clear; cleared with the other AOU_CORE registers by
AOU_CON0.AOU_SW_RESET, so the handler reads it before the reset) and the
mask is AOU_CORE.AOU_INTERRUPT_MASK.INT_FDI_LINK_DOWN_MASK (bit 10; the
mask gates the pin, not the status bit). Recovery is the LinkReset
sequence of xref:aou-ig-link-reset-sw-sequence[Section 6.5.3]. See
[.monospaced]#++DOC/MAS/interrupts-errors.adoc++# section 4.

[[aou-ig-activation-flow]]
== 6. Activation Flow

____________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________
*AOU_TOP users:* When using [.monospaced]#++AOU_TOP++#, FDI bringup (RESET to ACTIVE) is
handled by [.monospaced]#++AOU_FDI_BRINGUP_CTRL++# before protocol-level activation
begins. The protocol activation described in this section occurs after
[.monospaced]#++O_FDI_LINK_UP++# is asserted. See
xref:aou-ig-fdi-bringup-flow-aou_top-only[Section 6.6] for the FDI bringup
sequence.
____________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________

The Activation of AOU_CORE begins after the UCIe link has been
established. This is indicated by the *I_INT_FSM_IN_ACTIVE* signal of the
*AOU_CORE_TOP*, which stays asserted through Retrain and L1 and falls only
when the link is lost (xref:aou-ig-ucie-external-control-and-status[Section 3.12]). There is no
dependency between the activation of the local die and the remote die.
Each die may initiate the activation sequence independently, which means
the timing of sending *ActivateReq* can differ. Both dies must exchange
*ActivateReq* and *ActivateAck* messages to transition to the *ENABLED*
state, at which point credited messages can be transmitted.

A die sends an ActivateAck in response to an ActivateReq from the other
die while its own activation FSM is DISABLED or ACTIVATE. If the local
activation FSM is ENABLED, or is in DEACTIVATE, that ActivateReq is an
invalid activation message (see
[.monospaced]#++DOC/MAS/software-operation.adoc++# section 7.2.3) and
is not answered: AoU specification v0.8 treats it as an inconsistent
Req/Ack that moves the interface to its error state, in which nothing
is transmitted (sections 8.3.3 and 8.4). It means the remote die has
lost the activation state, for example because of a bug or a local
reset. The local die requests LinkReset at once. Software resets
AOU_CORE and both dies run activation again so they share one state.

[[aou-ig-deactivation-credit-rules]]
=== 6.1 Credits and Credited Messages During Deactivation

AOU_CORE follows the DEACTIVATE rules of AoU specification v0.8 section
8.4. Request-related messages (WriteReq, ReadReq, WriteData) and
response-related messages (ReadData, WriteResp) are managed separately,
so a deactivating link still drains the responses it owes and no
re-activation is needed to complete them. There is no configuration
for this behaviour.

* Request messages are not sent after the local DeactivateReq. A request
a local manager issues after it stays in AOU_CORE and raises
INT_ACTIVATE_START once the activation FSM is DISABLED.
* ReadData and WriteResp are still sent after the local DeactivateReq,
including the responses to requests the remote die sends after it.
* Request credits are advertised until the remote die's DeactivateReq
arrives. ReadData and WriteResp credits are advertised until the local
DeactivateReq is sent, which may be after the local DeactivateAck, so
the responses to the local die's own open requests can still arrive.
* A flit's header (MsgCredit) credits are sent with the flit: they are
consumed when the flit, or the half flit that carries the header, passes
the D2D adapter's flit-cancel window without being cancelled.
* In DISABLED both dies discard the credits they hold.

The full rules are in
xref:../MAS/software-operation.adoc#aou-731-deactivation-credit-rules[MAS Section 7.3.1].

[[aou-ig-activation-start]]
=== 6.2 Activation Start

Activation can be initiated by setting ACTIVATE_START SFR: In the
current implementation, credits are granted based on the depth of the RX
FIFO, so it is required to ensure that all messages in the RX FIFO are
popped before sending the ActivateReq message.

Activation START (via SFR AOU_INIT.ACTIVATE_START SFR)

* Activation can be triggered by setting ACTIVATE_START.
* Activation does not proceed until I_INT_FSM_IN_ACTIVE is asserted,
since no flits can be transmitted beforehand. Therefore, it is allowed
to set the ACTIVATE_START SFR before I_INT_FSM_IN_ACTIVE is asserted. If
it is set before the assertion, the activation process will
automatically proceed after I_INT_FSM_IN_ACTIVE becomes asserted.
* AOU_INIT.ACTIVATE_START SFR is automatically cleared to 0 once the
activation is completed and AOU_ACTIVATE_STATE transitions to ENABLED.

[[aou-ig-deactivation-start]]
=== 6.3 Deactivation Start

Deactivation is initiated by setting the AOU_INIT.DEACTIVATE_START
register. The DeactivateReq waits until the conditions in
xref:../MAS/software-operation.adoc#aou-71-sfr-setting[MAS Section 7.1]
are met, including the DEACTIVATE_TIME_OUT_VALUE quiet window. The sequence
is in the *Deactivation Sequence Flow* section below.

* AOU_INIT.DEACTIVATE_TIME_OUT_VALUE is the length of a quiet window on
the TX path, 2^(v + 3) core clock cycles for a programmed value v (8,
16, 32, 64, 128, 256, 512 or 1024; reset value 0 is 8). While the
activation FSM is ENABLED or DEACTIVATE, the window completes after
that many cycles with nothing to transmit, and it restarts when the TX
path accepts or still holds a message. It is held clear in DISABLED and
ACTIVATE.
* The window may already have elapsed before software writes
DEACTIVATE_START. When the TX path has been quiet for the whole window,
the DeactivateReq follows the write at once; the other deactivation
conditions still apply. When a message is still in the TX path, or one
is accepted after the write, the DeactivateReq waits until that traffic
has been gone for the full window.
* A response the local die still has to send keeps the window open.
Having received the responses to its own requests is a separate
condition. When the TX path is already idle, the programmed value adds
no further wait. A shorter value shortens only the wait after a message
that is still in the TX path.

The ACTIVATION_OP field encodes deactivation messages as follows:

* 2 = DeactivateReq
* 3= DeactivateAck

[[aou-ig-deactivation-sequence-flow]]
==== 6.3.1 Deactivation Sequence Flow

Each die sends its DeactivateReq once its own requests have completed
and answers the other die's DeactivateReq with a DeactivateAck; the
interface reaches DISABLED when both DeactivateAcks have been exchanged.
Between the two DeactivateReqs the die that deactivated first still
answers the other die's requests, and the other die keeps granting the
response credits those answers need (section 6.1). A remote
DeactivateReq raises INT_DEACTIVATE_START as a hint: software sets
DEACTIVATE_START once the local managers have stopped issuing requests.
xref:../MAS/software-operation.adoc#aou-734-deactivation-sequence-flow[MAS Section 7.3.4]
(Figures 26 and 27) shows the exchange when either die deactivates
first.

This system provides a bus cleanly-completion mechanism:

* Slave bus cleanly indicates whether the local die has received all
responses to the requests it sent to the remote die.
* Master bus cleanly indicates whether the remote die has received all
responses to the requests it sent to the local die.

After deactivation, the credit count is reset, and during the subsequent
activation process, credits are advertised based on the RX FIFO depth.
Therefore, before sending an ActivateReq, the local die must confirm that
all messages in the RX FIFO have been popped. To satisfy that condition,
no backpressure must occur on the local die's MI AW/AR/W channels.

[[aou-ig-pm-entry-linkreset-linkdisabled-sequence]]
=== 6.5 PM Entry / LinkReset / LinkDisabled Sequence

For PM entry / LinkReset / LinkDisable entry sequence, UCIE_CORE should
check AOU_CORE state and try to change state. For this sequence,
resolving pending AXI transactions is necessary.

Responses owed in either direction are delivered during the
deactivation itself (section 6.1). An AXI transaction can still be
pending once AOU_CORE is DISABLED only when a local manager issued a
request after the local DeactivateReq; AOU_CORE then raises
INT_ACTIVATE_START, and SW activates again to complete it.

[[aou-ig-pm-entry-sw-sequence]]
==== 6.5.1 PM Entry SW Sequence

1.  Stop the local managers from issuing requests, then write
AOU_INIT.DEACTIVATE_START to 1.
2.  Polling AOU_INIT.ACTIVATE_STATE_DISABLED and
AOU_INIT.SLV_TR_COMPLETE & AOU_INIT.MST_TR_COMPLETE. 2.1 If
INT_ACTIVATE_START is raised, an AXI transaction is still pending:
activate AOU_CORE, let it complete, and deactivate AOU_CORE again.
3.  Polling AOU_INIT.ACTIVATE_STATE_DISABLED and
AOU_INIT.SLV_TR_COMPLETE & AOU_INIT.MST_TR_COMPLETE.
4.  Do PM Entry Sequence on UCIE_CORE.

xref:../MAS/software-operation.adoc#aou-736-pm-entry--linkreset--linkdisabled-sequence[MAS Section 7.3.6]
(Figure 28) shows the sequence.

[[aou-ig-link-disable-sw-sequence]]
==== 6.5.2 Link Disable SW Sequence

Same as PM entry, before doing UCIe state transition, AOU_CORE needs to
be Disabled properly.

1.  Stop the local managers from issuing requests, then write
AOU_INIT.DEACTIVATE_START to 1.
2.  Polling AOU_INIT.ACTIVATE_STATE_DISABLED and
AOU_INIT.SLV_TR_COMPLETE & AOU_INIT.MST_TR_COMPLETE. 2.1 If
INT_ACTIVATE_START is raised, an AXI transaction is still pending:
activate AOU_CORE, let it complete, and deactivate AOU_CORE again.
3.  Polling AOU_INIT.ACTIVATE_STATE_DISABLED and
AOU_INIT.SLV_TR_COMPLETE & AOU_INIT.MST_TR_COMPLETE.
4.  Do LinkReset / LinkDisable Sequence on UCIE_CORE.

[[aou-ig-link-reset-sw-sequence]]
==== 6.5.3 Link Reset SW Sequence

If AOU_CORE faces an uncorrectable error (ex. AOU SPEC violation),
AOU_CORE sends LinkReset to CPU and D2D adapter. LinkReset indicates
that an error has occurred which requires the Link to go down.

While handling LinkReset, SW needs to do AOU_CORE SW reset by setting
AOU_CON0.AOU_SW_RESET.

Unlike the PM entry and Link Disable sequences, this one does not drain
the AXI traffic first: with the link down, nothing AOU_CORE holds could
complete. AOU_CON0.AOU_SW_RESET (like I_RESETN) loses every AXI
transaction in flight or queued in AOU_CORE, on the S and M ports of every
RP, without an error response, and the ports do not keep the AXI protocol
across it. The RX FIFOs reset with the core, so nothing received before the
reset is delivered after it. The AXI managers and subordinates attached to
the AoU ports are reset with AOU_CORE or recover on their own, as
xref:aou-ig-reset-domains[Section 3.1.1] requires; SW restarts the lost
traffic after re-activation.

SW learns of a LinkReset, Disabled or Adapter-reported LinkError that
took the link down while AoU was in use from INT_FDI_LINK_DOWN
(xref:aou-ig-interrupts[Section 5]) or from the UCIe controller; the
activation FSM is already DISABLED when the handler runs. The sequence
is the same: read AOU_INIT (the status bit is cleared with the other
registers by AOU_CON0.AOU_SW_RESET; write pass:[']1pass:['] clears it when the
handler does not reset the core), AOU_CON0.AOU_SW_RESET, restart the link
on the UCIe controller, reprogram the configuration registers,
ACTIVATE_START.

=== 6.6 FDI Bringup Flow (AOU_TOP only)

____________________________________________________________________________________________________________________________________________________________________

using [.monospaced]#++AOU_CORE_TOP++# directly, you must implement an equivalent FDI

[[aou-ig-overview]]
==== 6.6.1 Overview

[.monospaced]#++AOU_FDI_BRINGUP_CTRL++# manages the UCIe FDI state machine, handling
the four handshake pairs required to bring the FDI link from RESET to
ACTIVE, and follows the D2D adapter through LinkError, LinkReset,
Disabled, Retrain, and L1 entry/exit. It takes the link down only for an
error ([.monospaced]#++O_LP_LINKERROR++#) and never restarts it: a link-down for PM
entry, LinkReset or Link Disable, and training the link again, are done
by software on the UCIe controller (xref:aou-ig-bringup-sequence[Section 6.6.2]).
An AOU deactivation does not change the FDI link state. One sequence
diagram per case (bring-up, deactivation, link-down with AoU idle and in
use, LinkError from either side, Retrain, L1) is in
xref:../MAS/software-operation.adoc#aou-737-fdi-link-lifecycle-sequences[MAS Section 7.3.7].

The bringup FSM operates in the [.monospaced]#++I_CLK++# domain and uses 11 internal
states: RESET, WAIT_PRESENCE, WAKE_ASSERT, WAKE_WAIT_ACK, REQ_ACTIVE,
ACTIVE, RETRAIN, LINKERROR, L1, L1_CLK_WAKE and LINKDOWN. The status
output [.monospaced]#++O_FDI_FSM_STATE++# maps these to the UCIe
[.monospaced]#++pl_state_sts++# encoding (xref:aou-ig-fdi-bringup-status-aou_top-only[Section 3.16]).

Once the bringup FSM reaches ACTIVE, it asserts [.monospaced]#++O_INT_FSM_IN_ACTIVE++#
into [.monospaced]#++AOU_CORE_TOP++#, which enables protocol-level activation as
described in xref:aou-ig-activation-flow[Section 6]. The two status
outputs differ on purpose: [.monospaced]#++O_FDI_LINK_UP++# is 1 in ACTIVE only,
while [.monospaced]#++O_INT_FSM_IN_ACTIVE++# (link established) is set on entry to
ACTIVE and cleared on entry to LINKERROR, LINKDOWN or RESET, so it stays 1
through RETRAIN, L1, L1_CLK_WAKE and the wake handshake that ends an L1
(WAKE_ASSERT, WAKE_WAIT_ACK, REQ_ACTIVE, which are 0 on the cold bring-up
path). Its
falling edge is what raises [.monospaced]#++INT_FDI_LINK_DOWN++# in AOU_CORE when the
activation FSM is not DISABLED.

[[aou-ig-bringup-sequence]]
==== 6.6.2 Bringup Sequence

The normal (happy-path) bringup from cold reset proceeds as follows:

image::fdi-bringup-sequence.svg[Normal (happy-path) FDI bringup sequence from cold reset]

The steps in detail:

1.  *RESET*: After hardware reset, the FSM waits for PL to report
[.monospaced]#++pl_state_sts = RESET++# and assert [.monospaced]#++pl_inband_pres++# (remote die
detected).
2.  *WAIT_PRESENCE*: Remote die is present. The FSM asserts
[.monospaced]#++lp_rx_active_sts++# (if PL requests it) and waits for an activation
trigger. The trigger can be:
* [.monospaced]#++I_SW_ACTIVATE_START++# (top-level port)
* [.monospaced]#++I_INT_ACTIVATE_START++# (from the corepass:[']s activation controller)
* [.monospaced]#++I_PL_CLK_REQ++# (PL-initiated clock request)
3.  *WAKE_ASSERT / WAKE_WAIT_ACK*: The LP-initiated wake handshake.
[.monospaced]#++lp_wake_req++# is asserted and the FSM waits for [.monospaced]#++pl_wake_ack++#.
4.  *REQ_ACTIVE*: Wake handshake complete. The FSM drives
[.monospaced]#++lp_state_req = ACTIVE++# and waits for both [.monospaced]#++pl_state_sts = ACTIVE++# and
[.monospaced]#++pl_rx_active_req = 1++#.
5.  *ACTIVE*: The FDI link is up. [.monospaced]#++O_FDI_LINK_UP++# and
[.monospaced]#++O_INT_FSM_IN_ACTIVE++# are asserted. Protocol-level activation
(xref:aou-ig-activation-flow[Section 6]) can now proceed. The FSM stays
in ACTIVE across AOU deactivations and re-activations; it leaves only
on an error or on a state change the PL reports. In RETRAIN, L1 and
L1_CLK_WAKE, and through the wake handshake of an L1 exit,
[.monospaced]#++O_FDI_LINK_UP++# is 0 and [.monospaced]#++O_INT_FSM_IN_ACTIVE++#
stays 1; in LINKERROR, LINKDOWN and RESET both are 0.

*After a link-down*: after a LinkError (once [.monospaced]#++AOU_CON0.AOU_SW_RESET++#
has been applied, see below), or a LinkReset or Disabled the PL reports,
the FSM drives [.monospaced]#++lp_state_req = NOP++# with [.monospaced]#++lp_wake_req = 0++#,
follows the PL to Reset and waits in RESET for [.monospaced]#++pl_inband_pres++#,
exactly as after a cold reset. It gives no training trigger of its own.
Software restarts the link on the UCIe controller (the D2D adapterpass:[']s
Start UCIe Link Training, or the remote die trains), after which
[.monospaced]#++pl_inband_pres++# rises and bringup continues from step 2 with the
next activation request; software then re-activates AOU once
[.monospaced]#++O_FDI_LINK_UP++# is back. Each of these link-downs drops
[.monospaced]#++O_INT_FSM_IN_ACTIVE++#, and AOU_CORE raises
[.monospaced]#++INT_FDI_LINK_DOWN++# and returns its activation FSM to DISABLED if AoU
was in use (xref:aou-ig-interrupts[Section 5]). An activation request seen while the
FSM is in LINKERROR, LINKDOWN or RESET is dropped; the request that counts
is the one seen in WAIT_PRESENCE.

[[aou-ig-supported-state-transitions]]
==== 6.6.3 Supported State Transitions

[width="100%",cols="<34%,<33%,<33%",options="header",]
|=======================================================================
|From |To |Trigger
|Any state except LINKERROR |LINKERROR |[.monospaced]#++pl_state_sts = LinkError++#

|ACTIVE, RETRAIN |LINKERROR |[.monospaced]#++I_AOU_REQ_LINKRESET++# or
[.monospaced]#++I_SW_LINKERROR_INJECT++# (own request; drives [.monospaced]#++O_LP_LINKERROR++#).
Not taken in L1, L1_CLK_WAKE or the wake states: [.monospaced]#++I_AOU_REQ_LINKRESET++#
is a level and is acted on once the link is Active again (software exits L1 on
the UCIe controller first); an [.monospaced]#++I_SW_LINKERROR_INJECT++# pulse there is
ignored

|Any state except LINKERROR and LINKDOWN |LINKDOWN |[.monospaced]#++pl_state_sts++# =
LinkReset or Disabled

|RESET |WAIT_PRESENCE |[.monospaced]#++pl_state_sts = RESET++# AND [.monospaced]#++pl_inband_pres = 1++#

|WAIT_PRESENCE |WAKE_ASSERT |[.monospaced]#++I_SW_ACTIVATE_START++#, [.monospaced]#++I_INT_ACTIVATE_START++#
or [.monospaced]#++pl_clk_req = 1++#

|WAIT_PRESENCE |RESET |[.monospaced]#++pl_inband_pres = 0++#

|WAKE_ASSERT |WAKE_WAIT_ACK |Unconditional (1 cycle)

|WAKE_WAIT_ACK |REQ_ACTIVE |[.monospaced]#++pl_wake_ack = 1++#

|WAKE_WAIT_ACK, REQ_ACTIVE |RESET |[.monospaced]#++pl_inband_pres = 0++# AND
[.monospaced]#++pl_state_sts = RESET++#

|REQ_ACTIVE |ACTIVE |[.monospaced]#++pl_state_sts = ACTIVE++# AND [.monospaced]#++pl_rx_active_req = 1++#

|ACTIVE |RETRAIN |[.monospaced]#++pl_state_sts = Retrain++# (PL-initiated only)

|ACTIVE |L1 |[.monospaced]#++pl_state_sts = L1++# (PL-initiated only)

|ACTIVE |RESET |[.monospaced]#++pl_state_sts = RESET++#

|RETRAIN |ACTIVE |[.monospaced]#++pl_state_sts = ACTIVE++#. RETRAIN drives
[.monospaced]#++lp_state_req = NOP++# for one cycle, then Active (the NOP to Active
transition that ends a Retrain, UCIe r1.1 8.3.3.4).

|LINKERROR |RESET |[.monospaced]#++pl_state_sts = RESET++# AND
[.monospaced]#++AOU_CON0.AOU_SW_RESET++# applied since LINKERROR entry (either order)

|LINKDOWN |RESET |[.monospaced]#++pl_state_sts = RESET++#. LINKDOWN drives
[.monospaced]#++lp_state_req = NOP++#, which LinkReset and Disabled ignore; the PL
leaves for Reset on its own (software on the UCIe controller).

|L1 |L1_CLK_WAKE |[.monospaced]#++pl_clk_req = 1++#

|L1 |WAKE_ASSERT |Activate request

|L1 |RESET |[.monospaced]#++pl_state_sts = RESET++#

|L1_CLK_WAKE |WAKE_ASSERT |Unconditional (1 cycle, asserts [.monospaced]#++lp_clk_ack++#)
|=======================================================================

There is no transition out of ACTIVE on an AOU deactivation, and no
state requests Active except REQ_ACTIVE, ACTIVE and the Retrain exit.
Nothing in LINKERROR, LINKDOWN or RESET reacts to an activation request.

*LinkError recovery.* A LinkError may take the Adapter out of ACTIVE in
the middle of a flit in either direction. AOU_CORE's FDI data paths keep
the position of that flit, and only [.monospaced]#++AOU_CON0.AOU_SW_RESET++# clears
it, so the FSM holds the link down in LINKERROR
([.monospaced]#++lp_state_req = NOP++#, [.monospaced]#++O_FDI_FSM_STATE = LinkError++#,
[.monospaced]#++O_FDI_LINK_UP = 0++#) until software has applied that reset, whether
the LinkError came from the Adapter, from [.monospaced]#++O_AOU_REQ_LINKRESET++# or
from [.monospaced]#++I_SW_LINKERROR_INJECT++#. On its own request the FSM drives
[.monospaced]#++O_LP_LINKERROR++# until the PL reports LinkError. It requests nothing
to leave LinkError: the Adapter leaves for Reset on its own internal
request (software on the UCIe controller). [.monospaced]#++pl_clk_req++# is still
acknowledged meanwhile, but does not restart the link. Recovery is the
LinkReset sequence of
xref:../MAS/software-operation.adoc#aou-736-pm-entry--linkreset--linkdisabled-sequence[MAS Section 7.3.6]:
software observes [.monospaced]#++O_FDI_FSM_STATE = LinkError++# (or
[.monospaced]#++INT_REQ_LINKRESET++#, when AOU_CORE raised the error, or
[.monospaced]#++INT_FDI_LINK_DOWN++#, when the Adapter took the link down with AoU
in use), writes
[.monospaced]#++AOU_SW_RESET++#, reprograms the configuration registers, restarts
the link on the UCIe controller, and re-activates AOU with an activation
request. The FSM leaves LINKERROR once [.monospaced]#++pl_state_sts = RESET++# and
passes through RESET and WAIT_PRESENCE as after a cold reset
(xref:aou-ig-bringup-sequence[Section 6.6.2]). Integrators of
[.monospaced]#++AOU_CORE_TOP++# get the reset on [.monospaced]#++O_SW_RESET++#.

[[aou-ig-software-bringup-control]]
==== 6.6.5 Software Bringup Control

The [.monospaced]#++I_SW_ACTIVATE_START++# port on [.monospaced]#++AOU_TOP++# is *not SFR-mapped*.
It is a top-level pin that must be driven by external logic (e.g. a
system controller or GPIO). The bringup FSM ORs [.monospaced]#++I_SW_ACTIVATE_START++#
with the corepass:[']s internal [.monospaced]#++INT_ACTIVATE_START++# to form the combined
activation trigger, which is consumed in WAIT_PRESENCE (and in L1, where
it starts the wake handshake). There is no software pin to take the link
down or to retrain it (xref:aou-ig-fdi-bringup-software-control-aou_top-only[Section 3.15]).

_________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________
*Note (GAP-15):* The SFR register at address 0x8 bit[0]
([.monospaced]#++activate_start++#) feeds the protocol-level activation controller, not
the FDI bringup FSM. Writing this bit has no effect until the FDI link
is already in the ACTIVE state. To trigger cold-start FDI bringup via
software, assert [.monospaced]#++I_SW_ACTIVATE_START++# on the [.monospaced]#++AOU_TOP++# port or arrange
for PL to drive [.monospaced]#++pl_clk_req++#.
_________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________________

[[aou-ig-known-limitations]]
==== 6.6.6 Known Limitations

The current implementation covers the core FDI bringup happy path. The
following limitations apply (see [.monospaced]#++RTL/fdi-bringup-todo.md++# for the full
gap analysis):

[width="100%",cols="<50%,<50%",options="header",]
|=======================================================================
|ID |Description
|GAP-1 |No wake handshake timeout. If [.monospaced]#++pl_wake_ack++# never arrives, the
FSM hangs in ST_WAKE_WAIT_ACK indefinitely.

|GAP-3 |L2 (deep low-power) state is not implemented.

|GAP-4 |Closed. A PL-reported Disabled (or LinkReset) takes the FSM to
LINKDOWN: [.monospaced]#++O_FDI_LINK_UP++# and [.monospaced]#++O_INT_FSM_IN_ACTIVE++# drop
(AOU_CORE raises [.monospaced]#++INT_FDI_LINK_DOWN++# if AoU was in use),
[.monospaced]#++O_FDI_FSM_STATE++# reports Disabled (or LinkReset) as the PL did,
[.monospaced]#++lp_state_req++# is NOP and [.monospaced]#++lp_wake_req++# is 0. The FSM
leaves for RESET when the PL reports Reset. The FSM never requests
Disabled itself; software does that on the UCIe controller.

|GAP-9 |LP-initiated L1 entry is not supported (L1 entry is PL-initiated
only).

|GAP-15 |SFR [.monospaced]#++activate_start++# (0x8 bit[0]) is disconnected from the FDI
bringup FSM.
|=======================================================================

[[aou-ig-architecture]]
=== 7.1 Architecture

One bench with four tops. The main top, [.monospaced]#++tb/tb_top.sv++# (T1), puts
[.monospaced]#++AOU_TOP++# against layered models of the remote die; the other three
are smaller benches for the register file alone, the L3 protocol model
against the FDI checker, and the AXI agents in loopback.

....
                AXI SI (per RP)                          AXI MI (per RP)
  +------------------+             +------------------+             +------------------+
  | L4 AXI master    |  -------->  |     AOU_TOP      |  -------->  | L4 AXI slave     |
  | agents           |             |     (DUT)        |             | agents (memory)  |
  +------------------+             |                  |             +------------------+
  +------------------+             |                  |
  | APB agent + RAL  |..APB.......>|                  |
  +------------------+             +------------------+
                                     FDI LP  |  ^  FDI PL
                                             v  |
                                   +------------------+
                                   | L1 FDI agent     |  flit-level drive and monitor
                                   | L2 link state    |  PL link-state machine, bring-up
                                   | L3 AoU protocol  |  remote-die AoU model
                                   | L4 remote AXI    |  the remote die's AXI side
                                   +------------------+
                                   AOU_FDI_CHECKER (passive, on the FDI)
....

The remote die is modelled in four layers: L1 plays the Flit-Die
Interface, L2 the PL link-state machine and bring-up, L3 the AoU protocol
(message packing, credits, ordering), and L4 the AXI traffic on the remote
side. AXI traffic entering a local RP is checked end to end against what
the L4 remote model receives, and in the reverse direction. A passive
[.monospaced]#++AOU_FDI_CHECKER++# watches the FDI in both directions; its rules, and
those of the AXI, APB and register checkers, are listed with their IDs in
[.monospaced]#++uvm/env/checkers/rules.csv++#.

The DUT parameters of a build are selected by [.monospaced]#++CONFIG++#
([.monospaced]#++1x512-sp64++# by default: one RP at 512 bits, a 64-byte single-PHY
FDI). The other configurations cover one to four RPs, mixed RP widths of
256/512/1024 bits, 32/64/128-byte FDI, two-PHY FDI and the non-default
RX FIFO depths; [.monospaced]#++make configs++# prints the table.

=== 7.3 Running the Testbench

From the bench directory, fetch the pinned dependencies once and then
build and run:

[source,bash]
----
cd hw/ip/aou/dv
make setup                                   # uvm-core, OCAH library, z3, PeakRDL, pywellen into .deps/
make test                                    # build TB=t1 CONFIG=1x512-sp64, run aou_sanity_test
make build SIM=verilator                     # or SIM=vcs (default when vcs is on PATH)
make run TEST=aou_dp_random_test SEED=3 PLUSARGS='+dp_dir=both'
make run TEST=aou_sanity_test WAVES=1        # waves into the run directory (FSDB/FST)
make build TB=reg && make run TB=reg TEST=aou_reg_access_test
python3 scripts/run_list.py --items smoke    # the bring-up gate (4 scenarios)
python3 scripts/run_list.py --items functional -j 16 --rid nightly
make check-config                            # sim configs, testlists, rules, RAL and docs freshness
make lint                                    # check-config, then Verible and Verilator lint
----

Each run ends with a verdict ([.monospaced]#++PASS++#, [.monospaced]#++XFAIL++# or
[.monospaced]#++FAIL++#) written to its run directory under [.monospaced]#++out/++#;
[.monospaced]#++run_list.py++# collects them into [.monospaced]#++results.csv++# and exits
non-zero unless every run is PASS or XFAIL. Builds and runs go through LSF
when [.monospaced]#++bsub++# is available ([.monospaced]#++LSF=0++# runs on the current
host). CI runs [.monospaced]#++make check-config++#, builds the T1 and register
benches on Verilator and runs the T1 bench's [.monospaced]#++ci++# group (smoke, the
short lists and the datapath area) and the register bench's [.monospaced]#++smoke++#.

All register information lives in the SystemRDL source file
[.monospaced]#++csr/aou-core.rdl++#. Every output listed above is derived from this
single file -- there is no separate register spreadsheet or
hand-maintained IP-XACT register map.

....

[[aou-ig-planned-full-ip-xact-component-phase-2]]
=== 8.4 Planned: Full IP-XACT Component (Phase 2)

The Phase 1 IP-XACT output contains the [.monospaced]#++<memoryMaps>++# element only
(registers, fields, access types, reset values). A full IP-XACT
component -- including [.monospaced]#++<busInterfaces>++# (ARM AMBA AXI4 and APB3),
[.monospaced]#++<ports>++#, and [.monospaced]#++<model>++# parameters -- is planned for a later phase.

This is deferred because [.monospaced]#++AOU_CORE_TOP.sv++# uses SystemVerilog 2D packed
arrays for its per-RP AXI ports (e.g., [.monospaced]#++[RP_COUNT-1:0][AXI_ID_WD-1:0]++#),
which have no clean single-dimension representation in IP-XACT. Once a
wrapper module ([.monospaced]#++AOU_CORE_TOP_WRAP++#) is created that flattens these into
individual per-RP port signals, the full IP-XACT component will be
generated by merging the PeakRDL register map into a hand-authored
component template via [.monospaced]#++scripts/merge_ipxact.py++#.

==== 8.5.1 Clock Definitions

[cols=",,,",options="header",]

|Clock |Port |Frequency |Period
|[.monospaced]#++clk_core++# |[.monospaced]#++I_CLK++# |1 GHz |1.000 ns

[[aou-ig-io-delay-budgeting-strategy]]
==== 8.5.2 I/O Delay Budgeting Strategy

Two budgeting categories are used, based on whether the path between the
I/O port and the nearest internal flop is combinational or registered:

[width="100%",cols="21%,29%,30%,20%",options="header",]
|=======================================================================
|Path type |Internal budget |External budget |Rationale
|*Combinational* |50% of clock period |50% of clock period |Mux/decode
logic inside RTL takes some portion of cycle

|*Registered* |30% of clock period |70% of clock period |Short wire path
to first flop; external block gets more margin
|=======================================================================

*Interface classification summary:*

* *APB Slave*: Registered (via [.monospaced]#++ASYNC_APB_BRIDGE++# 2-flop synchroniser on
both sides). Constrained to [.monospaced]#++clk_apb++#.
* *AXI Slave inputs* (address, data, handshake to FIFOs): Registered --
input data is captured directly into FIFO register arrays.
* *AXI Slave outputs* (READY signals, read/bresp data): Combinational --
passes through arbitration muxes.
* *AXI Master outputs* (AR/AW/W channels): Combinational -- data passes
through FIFO read mux, arbitration mux ([.monospaced]#++AXI4MUX_3X1++#), and [.monospaced]#++REV_RS++#
mux.
* *AXI Master inputs* (R/B data, READY feedback): Combinational -- feeds
control logic and FIFO write.
* *FDI TX outputs* (DATA, VALID, IRDY): Combinational. STALLACK outputs
are registered. With [.monospaced]#++TX_NXT_PACKING_EN = 1++# the DATA output is driven from
a register in [.monospaced]#++AOU_TX_CORE++# through the FDI output mux only.
* *FDI RX inputs*: Combinational -- data/valid pass through an input
mux. [.monospaced]#++FLIT_CANCEL++# drives both sequential and combinational logic.
* *Interrupt/control signals*: Combinational.

[[aou-ig-clock-domain-crossings]]
==== 8.5.3 Clock Domain Crossings

The only CDC in AOU_CORE_TOP is between [.monospaced]#++clk_core++# and [.monospaced]#++clk_apb++#,
handled by the [.monospaced]#++ASYNC_APB_BRIDGE++# module which uses [.monospaced]#++AOU_SOC_SYNCHSR++#
(2-flop) synchronisers. The SDC uses [.monospaced]#++set_clock_groups -asynchronous++# to
exclude cross-domain paths from STA.

[[aou-ig-upf-power-intent]]
=== 8.6 UPF Power Intent

The current UPF defines a single always-on power domain ([.monospaced]#++PD_AOU_TOP++#)
covering the integration scope (the [.monospaced]#++AOU_TOP++# instance, which includes
[.monospaced]#++AOU_CORE_TOP++# and [.monospaced]#++AOU_FDI_BRINGUP_CTRL++#, when integrating via
[.monospaced]#++AOU_TOP++#; or the [.monospaced]#++AOU_CORE_TOP++# instance when integrating via
[.monospaced]#++AOU_CORE_TOP++# directly) with a [.monospaced]#++VDD++#/[.monospaced]#++VSS++# supply pair. No isolation,
retention, or level-shifting strategies are required at this time. When
power domains are introduced in the future, the UPF should be extended
with [.monospaced]#++create_power_domain++# for each switchable domain, along with
appropriate isolation and retention strategies.

[[aou-ig-library-cell-replacement]]
=== 8.7 Library Cell Replacement

The [.monospaced]#++RTL/LIB/++# directory contains three behavioral reference models that
are used by the design for reset infrastructure and clock-domain
crossing. These models are functionally correct for simulation but *must
be replaced* with process-appropriate implementations before synthesis
or tapeout.

[width="100%",cols="13%,8%,16%,9%,27%,27%",options="header",]
|=======================================================================
|Module |File |Parameters |Ports |Behavioral function |Where
instantiated
|[.monospaced]#++AOU_SOC_SYNCHSR++# |[.monospaced]#++RTL/LIB/AOU_SOC_SYNCHSR.v++# |[.monospaced]#++DW++# (width), [.monospaced]#++RST_VAL++#
(reset value), [.monospaced]#++DEPTH++# (2/3/4) |[.monospaced]#++I_CLK++#, [.monospaced]#++I_RESETN++#, [.monospaced]#++I_D[DW-1:0]++# ->

|[.monospaced]#++AOU_SOC_BUF++# |[.monospaced]#++RTL/LIB/AOU_SOC_BUF.v++# |[.monospaced]#++DW++# (width) |[.monospaced]#++I_A[DW-1:0]++# ->
[.monospaced]#++O_Y[DW-1:0]++# |Non-inverting buffer (identity: [.monospaced]#++O_Y = I_A++#)
|[.monospaced]#++AOU_CORE_TOP++# as [.monospaced]#++dft_persistent_buf_scan_resetn_sw++# (DFT persistent
buffer on scan reset)

*Replacement approaches:*

1.  *Drop-in replacement* -- Create new module definitions with the same
module names and identical port/parameter interfaces, backed by standard
cells or hard macros from the target process library. Replace the
corresponding files in the filelist ([.monospaced]#++RTL/LIB/filelist.f++#) with the new
implementations.
2.  *In-place wrapper* -- Edit the provided module shells directly,
replacing the behavioral [.monospaced]#++assign++#/[.monospaced]#++always++# bodies with instantiations of
target-library primitives while keeping the module name and port
interface unchanged.

*Important considerations:*

* [.monospaced]#++AOU_SOC_SYNCHSR++# is on the CDC path and must be replaced with a
foundry-qualified synchroniser cell (or equivalent hardened multi-flop
structure) to meet metastability MTBF requirements. The [.monospaced]#++DEPTH++#
parameter must be honoured.
* [.monospaced]#++AOU_SOC_GFMUX_LVT++# is on the reset mux path and must be replaced with
a glitch-free clock/reset mux cell to avoid glitches during reset
switching.
* [.monospaced]#++AOU_SOC_BUF++# is on the DFT scan-reset path. Replace with a buffer
cell that will be preserved through synthesis optimisation (typically
via a [.monospaced]#++dont_touch++# or equivalent attribute).
* The behavioral models can serve as a golden reference for verifying
functional equivalence of the replacements.

[[aou-ig-scan-friendly-cell-requirements]]
==== 8.7.1 Scan-Friendly Cell Requirements

Beyond functional correctness, each replacement cell must be compatible
with ATPG scan insertion and pattern generation. The behavioral models
have no scan awareness; the replacements must address this.

*[.monospaced]#++AOU_SOC_SYNCHSR++# -- Scan-safe synchronizer*

Standard multi-flop synchronizers cause X-propagation during scan shift
because the asynchronous input crossing from the other clock domain is
not controllable by the ATPG tool. The replacement synchronizer must be
*scan-safe* via one of the following approaches:

1.  *Built-in scan bypass mux* (preferred): The synchronizer cell
includes a scan-mode mux that bypasses the asynchronous first-stage flop
during shift. The ATPG tool holds the bypass active during shift and
restores normal operation for capture. This is the standard approach
used by foundry-provided synchronizer cells (e.g., [.monospaced]#++SDFF++#-based sync
cells with a scan-enable input).
2.  *ATPG tool constraint*: If the replacement cell does not have a
built-in bypass, the integrator must declare it as a synchronizer in the
ATPG tool so the tool forces the input to a known value during shift
(e.g., Synopsys [.monospaced]#++set_dft_signal -type constant++# on the synchronizer
input).

Foundry-provided synchronizer cells are strongly preferred because they
are pre-characterized for both metastability MTBF and scan testability.

*[.monospaced]#++AOU_SOC_GFMUX_LVT++# -- Clock/reset mux recognition*

This cell sits on the scan-mode reset mux path (see
xref:aou-ig-tiel_dft_modescan-usage[Section 3.13.1]). The replacement
must be recognized by the ATPG tool as a *clock or reset mux cell*, not
a generic data mux. If the tool treats it as a regular mux, it may
toggle [.monospaced]#++I_SEL++# during scan patterns, causing reset glitches that corrupt
shift-register state and invalidate test patterns.

The integrator should:

* Use a process library cell explicitly categorized as a clock/reset mux
(e.g., a cell from the librarypass:[']s ICG or clock-mux family).
* Apply the appropriate DFT tool attribute to prevent [.monospaced]#++I_SEL++# toggling
during scan. For example, in Synopsys DFT Compiler:
[.monospaced]#++set_dft_signal -view existing_dft -type ScanMux -port u_sw_reset_mux/I_SEL++#.
* Verify in the ATPG toolpass:[']s DFT rule check that the mux select is
classified as a test-mode signal, not a scannable data input.

*[.monospaced]#++AOU_SOC_BUF++# -- Optimization protection*

This buffer drives the tied-high scan-reset bypass value into
[.monospaced]#++u_sw_reset_mux++#. Without protection, the synthesis tool will optimize
it away (replacing it with a direct tie-off), which may cause the
downstream reset mux to be optimized or restructured in ways that break
the intended DFT architecture.

The replacement buffer must carry a [.monospaced]#++dont_touch++# or [.monospaced]#++size_only++#
attribute (the specific attribute name depends on the synthesis tool) to
ensure it survives all optimization passes, including:

* Logic optimization and constant propagation
* Incremental optimization during place-and-route
* Post-route optimization
