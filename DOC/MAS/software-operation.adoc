For details on the ACTIVATE and DEACTIVATE SFRs, please refer to xref:aou-73-activation-deactivation-flow[Section 7.3]: Activation & Deactivation Flow.

*AOU_INIT.ACTIVATE_START*

* After the link is established (I_INT_FSM_IN_ACTIVE asserted), AOU_CORE can send or receive an ActivateReq message to complete the first activation handshake. A further ActivateReq once the FSM is ENABLED is an invalid activation message; see xref:aou-723-linkreset-error-reporting[Section 7.2.3].

* AoU Activation Request can only be triggered by AOU_INIT.ACTIVATE_START, and it is allowed to be set before and after the completion of the UCIe Link-up.

*AOU_INIT.DEACTIVATE_START*

* AOU_CORE must exchange both DeactivateReq and DeactivateAck messages before the UCIe Core transitions to the Link Down state.
* The DEACTIVATE_START field in AOU_INIT initiates deactivation and ensures that a DeactivateReq is issued only after both conditions below are satisfied:
1.  All outstanding responses to remote die requests have been completed.
2.  No additional messages remain to be transmitted within a window defined by *TIME_OUT_VALUE.*
* *AOU_INIT.DEACTIVATE_TIME_OUT_VALUE* configures the timeout value used for this condition. This field is 3 bits wide and encodes a timeout of *2^(DEACTIVATE_TIME_OUT_VALUE + 3)* cycles.

*MAX BURSTLEN*

* The *MAX_AWBURSTLEN* and *MAX_ARBURSTLEN* register fields define the maximum burst length that the splitter may issue to the local bus.
* The splitter inside *AOU_CORE* issues AXI transfers with burst lengths less than or equal to the configured values (*MAX_AWBURSTLEN*, *MAX_ARBURSTLEN*).
* If *AOU_CORE* receives a larger burst length from the remote die, the splitter divides it into smaller bursts based on MAX_AxBURSTLEN.
* Since the splitter only supports maximum burst lengths of the form 2^n - 1, the field must be configured with one of the following: 0, 1, 3, 7, 15, 31, 63, 127 or 255. The SFR stores 15 if any other value is written; read the field back to confirm the accepted value.

*ACTIVATE_STATE_ENABLED/DISABLED*

* This signal indicates the activation status of the AOU_ACTIVATION_CTRL.
* The ENABLE signal is asserted to indicate that activation has been completed.

The DISABLED signal is asserted to indicate that deactivation has been completed.

*MST_TR_COMPLETE/SLV_TR_COMPLETE*

* This signal indicates that there are no pending transactions in both local die and remote die.
* SLV_TR_COMPLETE additionally requires WRITE_EARLY_RESPONSE_RPn.WRITE_RESP_DONE = 1 on every RP: a write that received an early B response counts as pending until its actual B response has arrived from the remote die.

*ACK_TIME_OUT_VALUE/MSG_CREDIT_TIME_OUT_VALUE*

* After sending an AoU Activation/Deactivation Request message, if an Ack message is not received within the specified ACK_TIME_OUT_VALUE, a LinkReset interrupt is sent to the SW.
* After receiving the Activation Ack message from the remote die, if a creditgrant message is not received within the specified MSGCREDIT_TIME_OUT_VALUE, a LinkReset interrupt is sent to the SW.
* These fields are 3 bits wide and encode a timeout of 2^(TIME_OUT_VALUE + 18) core clock cycles.

*WRITE_EARLY_RESPONSE*

* For the EARLY_RESPONSE_EN or EARLY_ALWAYS_EN SFR setting to enable or disable early response, there must be no pending write requests (WRITE_RESP_DONE = 1).
* EARLY_RESPONSE_EN: If this field is set(1), It performs the early response function for bufferable writes (AWCACHE[0] = 1). Exclusive writes (AWLOCK = 1) never receive an early response.
* EARLY_ALWAYS_EN: If this field is set(1) together with EARLY_RESPONSE_EN, every non-exclusive write receives the early response regardless of AWCACHE[0].
* WDT_EN / WRITE_EARLY_RESPONSE_WDT_CTL.WDT_THRESHOLD: enable and threshold of the write-transaction watchdog; see xref:aou-726-write-transaction-watchdog[Section 7.2.6].
* WDT_TRANS_TIMEOUT_ERR: set when the watchdog of this RP expires; source of the INT_EARLY_WDT_ERR interrupt. Writing 1 clears it.
* WRITE_RESP_DONE: It indicates that there are no pending write requests and all write responses have been received from the remote die.
* WRITE_RESP_ERR: It indicated that although the early response feature was enabled and an early response has already been delivered to the local die, an error occurred later in the write response received from the remote die. The BRESP value of the error is stored in WRITE_RESP_ERR_TYPE_INFO, and the BID of the transaction that caused the error is stored in WRITE_RESP_ERR_ID_INFO SFR. When an error occurs, an interrupt is generated. Afterward, writing 1 to the WRITE_RESP_ERR SFR clears ERR_TYPE_INFO, ERR_ID_INFO, and RESP_ERR.

*Low Power mode*

* For lowering power, AOU_CORE uses low power mode. By setting AOU_CON0.TX_LP_MODE = 1, AOU_CORE only sends payload to FDI when there are remaining AXI messages to send. Since AOU_CORE need to send Credit when there are no remaining AXI messages, by setting AOU_CON0.TX_LP_MODE_THRESHOLD value, SW can configure the message transmission frequency.
* AOU_CON0.TX_LP_MODE_THRESHOLD = 0 selects a fully-gated low-power mode: the periodic heartbeat is disabled and the TX only launches an FDI flit when there is real work to send (AXI traffic, CrdtGrant credit-return messages, or pending MsgCredit-header credits). Once a flit is started it always finishes; any granule slots that were not filled are sent as zeros and the corresponding MsgStart bits are 0.
* AOU_CON0.TX_LP_MODE and AOU_CON0.TX_LP_MODE_THRESHOLD are static configuration. Program them only while the activation FSM is DISABLED (ACTIVATE_STATE_DISABLED = 1): before AOU_INIT.ACTIVATE_START, or after a deactivation has completed. They must not be changed while the link is activating, ENABLED or deactivating; the TX core may be in the middle of a flit, and the flit is not preserved across a change of mode.

[[aou-722-axi-id-mismatch-error]]
==== 7.2.2. AXI ID Mismatch Error

AOU_CORE can detect AXI ID mismatches on both the manager and subordinate interfaces. A mismatch occurs when a B or R response arrives with an AXI ID that does not correspond to any outstanding request.

*Manager side.* The split/aggregator path ([.monospaced]#++AOU_AXI_SPLIT_TR++# / [.monospaced]#++AOU_AXI4MUX_3X1_TOP++#) maintains pending-ID tables for both read and write transactions ([.monospaced]#++AOU_SPLIT_RD_PENDING_INFO++# and [.monospaced]#++AOU_SPLIT_WR_PENDING_INFO++#). When a B response arrives with an ID that does not match any pending write entry, [.monospaced]#++SPLIT_BID_MISMATCH_ERR++# is asserted and the offending ID is captured in [.monospaced]#++SPLIT_BID_MISMATCH_INFO++#. The same logic applies to R responses via [.monospaced]#++SPLIT_RID_MISMATCH_ERR++# and [.monospaced]#++SPLIT_RID_MISMATCH_INFO++#. These fields are in the per-RP [.monospaced]#++ERROR_INFO_RPn++# register (RP0 at 0x0024, RP1 at 0x003C, RP2 at 0x0054, RP3 at 0x006C). SW clears each error by writing 1 to the corresponding W1C bit. The aggregate interrupt is [.monospaced]#++INT_MI0_ID_MISMATCH++#.

*Table depth and backpressure.* Each pending-ID table is sized by [.monospaced]#++M_RD_MO_CNT++# / [.monospaced]#++M_WR_MO_CNT++# (default 32): the number of remote requests the RP keeps in service at its manager port. An entry is allocated on the handshake of the first split-AR or split-AW issued for a request and freed when the R (with RLAST) or B response of its last sub-burst completes; the entry counts the sub-bursts still to complete. A request the splitter divides therefore holds one entry for all of its sub-bursts, and the manager port may carry more AXI bursts than the table depth: up to [.monospaced]#++M_RD_MO_CNT++# (or [.monospaced]#++M_WR_MO_CNT++#) times the sub-bursts per request (xref:{aou-architecture-xref}#aou-362-burst-splitting[Section 3.6.2]). When all entries are occupied, the [.monospaced]#++O_AR_Slot_Available_Flag++# / [.monospaced]#++O_AW_Slot_Available_Flag++# signal goes low, which suppresses the first sub-burst of any new request and effectively deasserts ARREADY / AWREADY toward the upstream path; the remaining sub-bursts of requests already in the table continue to issue. This is backpressure, not an error \-- no entries are overwritten or dropped, and the table cannot overflow during correct operation.

*No disable mechanism.* There is no RTL parameter or SFR to disable the pending-ID tables or the mismatch check. The interrupt can be masked via [.monospaced]#++AOU_INTERRUPT_MASK.INT_MI0_ID_MISMATCH_MASK++# [3], but this only suppresses the interrupt signal. The tables continue to operate, backpressure still applies when full, and the sticky error bits in [.monospaced]#++ERROR_INFO_RPn++# are still set on a mismatch.

*Subordinate side.* An analogous pending-ID table exists in [.monospaced]#++AOU_SLV_AXI_INFO++#, with SFR fields in [.monospaced]#++AXI_SLV_ID_MISMATCH_ERR_RPn++# (RP0 at 0x0034, RP1 at 0x004C, RP2 at 0x0064, RP3 at 0x007C). However, the subordinate-side mismatch outputs are currently tied to 0 in RTL; the SFR fields are allocated but will always read 0. The aggregate interrupt [.monospaced]#++INT_SI0_ID_MISMATCH++# will therefore never fire in the current implementation.

[[aou-723-linkreset-error-reporting]]
==== 7.2.3. LinkReset Error Reporting

When AOU_CORE detects a protocol-level error during activation or deactivation, it asserts [.monospaced]#++O_AOU_REQ_LINKRESET++# (to FDI) and [.monospaced]#++INT_REQ_LINKRESET++# (to SW). Both signals share the same net and are the logical OR of the four sub-conditions below, each gated by its mask bit in [.monospaced]#++AOU_INTERRUPT_MASK++#: a masked cause raises neither the interrupt nor the request to the D2D adapter. The request is a level, held while the sticky status bit is set. The bringup controller acts on it while the link is Active or in Retrain; a request raised while the link is in L1, or exiting it, is deferred until the link is next Active, so SW that meets [.monospaced]#++ACT_ACK_ERR++# after an [.monospaced]#++ACTIVATE_START++# written in L1 (xref:aou-732-activation-start[Section 7.3.2]) exits L1 on the UCIe controller first and clears the status only after the D2D adapter has reported LinkError; clearing it earlier (W1C or [.monospaced]#++AOU_SW_RESET++#) withdraws the request and leaves the link in L1 with AOU_CORE [.monospaced]#++DISABLED++#, which SW then recovers by re-activating. After handling the interrupt, SW must perform a LinkReset sequence.

All LinkReset-related SFR fields reside in [.monospaced]#++LP_LINKRESET++# (0x0010).

*Activate/Deactivate Ack Timeout.* After sending an ActivateReq or DeactivateReq message, a counter begins. If the remote die does not return an Acknowledge within 2^([.monospaced]#++ACK_TIME_OUT_VALUE++# + 18) core clock cycles, the timeout fires. [.monospaced]#++ACK_TIME_OUT_VALUE++# [13:11] is 3 bits wide with a default of 4, giving a default timeout of 2^22 = ~4M cycles. The sticky error bits are [.monospaced]#++ACT_ACK_ERR++# [7] and [.monospaced]#++DEACT_ACK_ERR++# [6], both W1C.

*Invalid ACTMSG.* The activation FSM ([.monospaced]#++AOU_ACTIVATION_CTRL++#) checks each received activation opcode against the current state. An opcode that is not permitted sets [.monospaced]#++INVALID_ACTMSG_ERR++# [1] and captures the offending 4-bit opcode in [.monospaced]#++INVALID_ACTMSG_INFO++# [5:2]. Clear via W1C.

[cols="1,2",options="header"]
|===
|State |Permitted opcodes
|DISABLED, ACTIVATE |ActivateReq and ActivateAck. DeactivateReq and DeactivateAck are invalid.
|ENABLED, DEACTIVATE |DeactivateReq and DeactivateAck. ActivateReq and ActivateAck are invalid.
|===

An ActivateReq or ActivateAck received after the activate handshake has completed ([.monospaced]#++ENABLED++#), or while deactivation is in progress ([.monospaced]#++DEACTIVATE++#), means the remote die no longer agrees on link state: a bug, a local reset, or a similar loss of state. A late ActivateReq is not a new activation. Neither message is answered: the out-of-step Req/Ack is an error (AoU specification v0.8 section 8.3.3), and an interface in error transmits nothing (section 8.4), so the local die sends no ActivateAck. In either case, the local die requests LinkReset. Software resets AOU_CORE ([.monospaced]#++AOU_CON0.AOU_SW_RESET++#) and both dies run activation again, as described in xref:aou-736-pm-entry--linkreset--linkdisabled-sequence[Section 7.3.6].

*MsgCredit Timeout.* After the local die receives ActivateAck, it expects a CreditGrant message from the remote die indicating the number of resource planes. If no CreditGrant arrives within 2^([.monospaced]#++MSGCREDIT_TIME_OUT_VALUE++# + 18) core clock cycles, [.monospaced]#++MSGCREDIT_ERR++# [0] is set. [.monospaced]#++MSGCREDIT_TIME_OUT_VALUE++# [10:8] defaults to 4. Clear via W1C.

[[aou-724-rb-response-error-debug-fifo]]
==== 7.2.4. R/B Response Error Debug FIFO

When the manager interface receives an AXI B or R response with a non-OKAY status (SLVERR or DECERR), AOU_CORE captures the error details in a dedicated per-RP FIFO so that the remote die can retrieve them via AXI read.

*FIFO structure.* The [.monospaced]#++AOU_ERROR_INFO++# module (one instance per RP) implements a 4-entry circular FIFO. Each entry stores:

[cols="<,<,<",options="header",]
|=========================================================
|Field |Width |Description
|AXI ID |AXI_ID_WD |ID of the failing transaction
|AXI ADDR |AXI_ADDR_WD |Address of the failing transaction
|RESP |2 bits |BRESP or RRESP value
|=========================================================

Both BRESP and RRESP errors can be pushed simultaneously (two entries in one cycle). If the FIFO is full, new errors are silently dropped.

*Enabling access.* Before the remote die can read error information, SW must:

1.  Set [.monospaced]#++AOU_CON0.RPn_ERROR_INFO_ACCESS_EN++# [27:24] to 1 for the target RP.
2.  Configure the dedicated address window by writing the upper 32 bits to [.monospaced]#++AXI_ERROR_INFO0_RPn.DEBUG_UPPER_ADDR++# and the lower 32 bits to [.monospaced]#++AXI_ERROR_INFO1_RPn.DEBUG_LOWER_ADDR++#.

The [.monospaced]#++AOU_AXIMUX_1XN_SS++# address decoder routes any AXI transaction whose address matches [.monospaced]#++{DEBUG_UPPER_ADDR, DEBUG_LOWER_ADDR}++# to the [.monospaced]#++AOU_ERROR_INFO++# module instead of the normal datapath.

*Read protocol.* The remote die issues an AXI read (AR) to the configured debug address. The module returns the FIFO head entry on RDATA (containing the concatenated ID, address, and response fields) with RLAST = 1.

*Pop protocol.* To advance to the next entry, the remote die issues a dummy AXI write (AW + W) to the same debug address. The simultaneous AW and W handshake advances the FIFO read pointer, discarding the head entry. A B response (OKAY) is returned.

The typical access sequence is: read the head entry, then pop it, and repeat until no more entries remain.

[[aou-726-write-transaction-watchdog]]
==== 7.2.6. Write Transaction Watchdog

Once an early OKAY has been returned, the local AXI manager has no way to notice that the remote die never completed the write. The write-transaction watchdog in each RP's early response controller detects this: with [.monospaced]#++WRITE_EARLY_RESPONSE_RPn.WDT_EN = 1++# it counts I_CLK cycles in which the RP has writes outstanding (AW accepted, actual B not yet received) and neither an AW nor a B handshake occurs. Either handshake restarts the count. When it reaches [.monospaced]#++WRITE_EARLY_RESPONSE_WDT_CTL.WDT_THRESHOLD++# (0x0080, shared by all RPs, reset 0xC3500 = 800000 cycles), [.monospaced]#++WRITE_EARLY_RESPONSE_RPn.WDT_TRANS_TIMEOUT_ERR++# is set and [.monospaced]#++INT_EARLY_WDT_ERR++# is asserted unless [.monospaced]#++AOU_INTERRUPT_MASK.INT_EARLY_WDT_MASK++# is set.

Enable sequence:

1.  Write the threshold to [.monospaced]#++WRITE_EARLY_RESPONSE_WDT_CTL.WDT_THRESHOLD++#. Choose a value well above the longest expected write round trip, including remote-die back-pressure.
2.  Set [.monospaced]#++WDT_EN++# in each RP's [.monospaced]#++WRITE_EARLY_RESPONSE_RPn++#, normally together with [.monospaced]#++EARLY_BRESP_EN++#. The watchdog counts whether or not early response is enabled, so it can also be used as a plain write-completion timeout.

On [.monospaced]#++INT_EARLY_WDT_ERR++#:

1.  Read [.monospaced]#++WRITE_EARLY_RESPONSE_RPn.WDT_TRANS_TIMEOUT_ERR++# of every RP to find the RP whose writes stalled; [.monospaced]#++WRITE_RESP_DONE = 0++# on that RP confirms that writes are still outstanding.
2.  Write 1 to [.monospaced]#++WDT_TRANS_TIMEOUT_ERR++# to clear the status and the interrupt. The watchdog of that RP fires once: after a timeout its timer is held cleared and it does not re-arm until the next reset ([.monospaced]#++I_RESETN++# or [.monospaced]#++AOU_CON0.AOU_SW_RESET++#), so clearing the bit does not by itself restore hang detection. Toggling [.monospaced]#++WDT_EN++# does not re-arm it either.
3.  Recover the link as for a protocol error: the outstanding writes will not complete, so [.monospaced]#++SLV_TR_COMPLETE++# stays 0 and deactivation cannot finish. Apply [.monospaced]#++AOU_CON0.AOU_SW_RESET++# or request LinkReset as described in xref:aou-736-pm-entry--linkreset--linkdisabled-sequence[Section 7.3.6].

[[aou-73-activation-deactivation-flow]]
=== 7.3. Activation & Deactivation Flow

The Activation of AOU_CORE begins after the UCIe link has been established. This is indicated by the *I_INT_FSM_IN_ACTIVE* signal of the *AOU_CORE_TOP*: it rises once the link has first reached Active, stays asserted through Retrain and L1, and falls only when the link is lost (LinkError, LinkReset, Disabled or Reset).

The activation FSM leaves any state for [.monospaced]#++DISABLED++# on an error (AoU specification v0.8 section 8.3.3). The errors are the four LinkReset causes of xref:aou-723-linkreset-error-reporting[Section 7.2.3] (Activate-ack timeout, Deactivate-ack timeout, MsgCredit timeout, invalid activation message) and the loss of the FDI link while the FSM is in [.monospaced]#++ACTIVATE++#, [.monospaced]#++ENABLED++# or [.monospaced]#++DEACTIVATE++#, which raises [.monospaced]#++INT_FDI_LINK_DOWN++# (xref:aou-736-pm-entry--linkreset--linkdisabled-sequence[Section 7.3.6]). In both cases the handshake registers and the Ack and MsgCredit time-out waits are cleared, so no ActivateAck or DeactivateAck is sent afterwards, no second error is reported for the abandoned handshake, and [.monospaced]#++AOU_INIT.ACTIVATE_STATE_DISABLED++# reads 1.

There is no dependency between the activation of the local die and the remote die. Each die may initiate the activation sequence independently, which means the timing of sending *ActivateReq* can differ. Both dies must exchange *ActivateReq* and *ActivateAck* messages to transition to the *ENABLED* state, at which point credited messages can be transmitted.

[[aou-732-activation-start]]
==== 7.3.2. Activation start

Activation can be initiated by setting ACTIVATE_START SFR: In the current implementation, credits are granted based on the depth of the RX FIFO, so it is required to ensure that all messages in the RX FIFO have been popped before sending the ActivateReq message.

Activation START(via SFR AOU_INIT.ACTIVATE_START SFR)

* Activation can be triggered by setting ACTIVATE_START.
* Activation does not proceed until I_INT_FSM_IN_ACTIVE is asserted (link established), since no flits can be transmitted beforehand. Therefore, it is allowed to set the ACTIVATE_START SFR before I_INT_FSM_IN_ACTIVE is asserted. If it is set before the assertion, the activation process will automatically proceed after I_INT_FSM_IN_ACTIVE becomes asserted. I_INT_FSM_IN_ACTIVE stays asserted through Retrain and L1, so an ACTIVATE_START written then starts the handshake at once; the ActivateReq waits in the TX path until the D2D adapter accepts flits again, and the Ack timer (2^(18 + ACK_TIME_OUT_VALUE) cycles, xref:aou-723-linkreset-error-reporting[Section 7.2.3]) runs from the write, not from the adapter's acceptance, so an L1 that outlasts it ends in ACT_ACK_ERR. That is intended: the time-out is an error host SW understands and handles like any other ACT_ACK_ERR (xref:aou-723-linkreset-error-reporting[Section 7.2.3]); no link-state qualifier delays the timer. The write does not wake a link in L1: the bringup controller wakes it on the D2D adapter's pl_clk_req, on I_SW_ACTIVATE_START, or on INT_ACTIVATE_START (a pending local AXI transaction or a received ActivateReq while ACTIVATE_START is 0), so SW that activates from L1 exits L1 on the UCIe controller as in xref:aou-736-pm-entry--linkreset--linkdisabled-sequence[Section 7.3.6].
* AOU_INIT.ACTIVATE_START SFR is automatically cleared to 0 once the activation is completed and AOU_ACTIVATE_STATE transitions to ENABLED.

==== 7.3.3. Deactivation start

The detailed conditions and sequence for deactivation can be found in the *Deactivation Sequence Flow* section. This section will only describe AOU_INIT.DEACTIVATE_TIME_OUT_VALUE SFR.

* When software initiates a DeactivateReq by setting the SFR, there may still be outstanding requests that have not yet reached out AOU_CORE.
* To handle this safely, a timeout mechanism is implemented to ensure that no valid packets remain in the AOU_TX_CORE.
* If software guarantees that all responses to its issued requests have been received before setting the deactivation start SFR, the deactivate TIME_OUT_VALUE(AOU_INIT.DEACTIVATE_TIME_OUT_VALUE SFR) can be safely configured to a shorter duration.

[[aou-734-deactivation-sequence-flow]]
==== 7.3.4. Deactivation Sequence Flow

Once the local die issues a DeactivateReq, it can no longer provide responses to transactions initiated by the remote die. If the remote die continues to send requests or waits for responses without being notified, it may enter a hang state. To manage this safely, the remote die must take explicit action upon receiving a DeactivateReq: 1. Immediately generate an interrupt to the CPU to inform the system software that a DeactivateReq has been received and that it must set the DEACTIVATE_START SFR.

Although deactivation of the local die and the remote die operate independently, it is essential at the system level to communicate the deactivation & activation state through interrupts. This ensures that system software is explicitly informed of deactivation events and prevents the remote die from continuing to expect response that will never arrive, thereby avoiding hang conditions. This approach guarantees that once deactivation is initiated, both dies can coordinate the transition into safe and consistent DISABLED state.

If the software on both dies can explicitly coordinate to guarantee that all outstanding transactions have been completed and that no new transactions will be issued, then such an complicated implementation would not be necessary.

This system provides a bus cleany mechanism, tracked inside AOU_CORE and reported in AOU_INIT:

* SLV_TR_COMPLETE (subordinate bus cleanly) indicates whether the local die has received all responses to the requests it sent to the remote die. Writes that received an early B response count until their actual B response arrives (WRITE_EARLY_RESPONSE_RPn.WRITE_RESP_DONE = 1 on every RP), so deactivation waits for them.
* MST_TR_COMPLETE (manager bus cleanly) indicates whether the remote die has received all responses to the requests it sent to the local die.

After the local die sends a DeactivateReq, if the remote die issues a new request and expects a response, the system must re-enter the activation sequence before any response can be provided.

Before sending a new ActivateReq, the Rx FIFO must be completely emptied - that is, all messages must be popped. After deactivation, the credit count is reset, and during the subsequent activation process, credits are advertised based on the RX FIFO depth. Therefore, before sending an ActivateReq, the local die must confirm, as described in the local diepass:[']s sequence 10.1, that all messages in the RX FIFO have been popped.

To meet satisfy the condition in the local diepass:[']s sequence 10.1, no backpressure must occur on the local diepass:[']s MI AW/AR/W channels.

[[aou-735-activationdeactivation-interrupt]]
==== 7.3.5. Activation/Deactivation Interrupt

*INT_ACTIVATE_START*

* When this interrupt is detected, AOU_INIT.ACTIVATE_START SFR must be set to 1.
* When AOU_INIT.ACTIVATE_STATE_ENABLED becomes 1, write 1 to clear the AOU_INIT.INT_ACTIVATE_START W1C SFR.
* An interrupt occurs when AOU_INIT.ACTIVATE_START SFR is not set and any of the following conditions are met:
1.  There is a message to send
** When AOU_CON0.CREDIT_MANAGE = 0, if a new request arrives from the remote die after the local die has sent a DeactivateReq, this interrupt is asserted because the local die must return a response.
** When AOU_CON0.CREDIT_MANAGE = 1, this interrupt can also be asserted if a new request arrives after the remote die has sent a DeactivateReq.
2.  There is a response to be received: the local die has sent requests to the remote die whose responses have not yet arrived (AOU_INIT.SLV_TR_COMPLETE == 0)
** When AOU_CON0.CREDIT_MANAGE = 0, this interrupt can be asserted if the local die issues new AXI requests after the remote die has sent a DeactivateReq.
3.  An ActivateReq message is received from the remote die, and the activation handshake has not yet completed (the FSM is DISABLED or ACTIVATE). An ActivateReq received while ENABLED is [.monospaced]#++INVALID_ACTMSG++# and requests LinkReset (xref:aou-723-linkreset-error-reporting[Section 7.2.3]), not this interrupt.

*INT_DEACTIVATE_START*

* When AOU_CON0.CREDIT_MANAGE = 0: if the interrupt is detected, the manager IP must stop sending new request messages and AOU_INIT.DEACTIVATE_START SFR must be set to 1.
* When AOU_CON0.CREDIT_MANAGE = 1: if the interrupt is detected, this serves only as a hint that the remote die intends to deactivate. The local die can continue sending request messages. Once all messages have been sent, AOU_INIT.DEACTIVATE_START SFR must be set. Otherwise, the remote die may end up in a state where it can never send requests again.
* When AOU_INIT.ACTIVATE_STATE_DISABLED becomes 1, write 1 to clear the AOU_INIT.INT_DEACTIVATE_START W1C SFR.
* An interrupt is asserted when AOU_INIT.DEACTIVATE_START SFR is not set and the local die receives a DeactivateReq message from the remote die.

* *LinkReset sequence*

If AOU_CORE faces uncorrectable error (ex. AOU SPEC violation), AOU_CORE sends LinkReset to CPU and D2D adapter. LinkReset indicates that an error has occurred which requires the Link to go down.

While handling LinkReset, SW needs to do AOU_CORE SW reset by setting AOU_CON0.AOU_SW_RESET.
If the link is in L1 when AOU_CORE raises the request (an Ack time-out on an [.monospaced]#++ACTIVATE_START++# written in L1), the request is held until the link is Active again (xref:aou-723-linkreset-error-reporting[Section 7.2.3]): SW exits L1 on the UCIe controller first, waits for the D2D adapter to report LinkError, and only then applies [.monospaced]#++AOU_SW_RESET++#.
SW learns that the link went down (LinkReset, Disabled, or a LinkError the D2D adapter entered on its own) from [.monospaced]#++INT_FDI_LINK_DOWN++# (status [.monospaced]#++AOU_INIT.INT_FDI_LINK_DOWN++#, raised when [.monospaced]#++I_INT_FSM_IN_ACTIVE++# falls with the activation FSM in ACTIVATE, ENABLED or DEACTIVATE, or in DISABLED with an ActivateReq outstanding), or from the UCIe controller. The activation FSM is already [.monospaced]#++DISABLED++# when the handler runs; the sequence itself is unchanged: read [.monospaced]#++AOU_INIT++#, [.monospaced]#++AOU_SW_RESET++#, restart the link on the UCIe controller, reprogram the configuration registers, [.monospaced]#++ACTIVATE_START++#. The status bit is cleared with the other registers by [.monospaced]#++AOU_SW_RESET++# (write 1 clears it when the core is not reset; as for the other W1C bits of [.monospaced]#++AOU_INIT++#, the write also lands on the register's RW fields, so SW writes back the [.monospaced]#++ACTIVATE_START++#, [.monospaced]#++DEACTIVATE_START++# and [.monospaced]#++DEACTIVATE_TIME_OUT_VALUE++# values it wants to keep) and is not set again by the restart. A link lost with local AXI transactions pending also raises [.monospaced]#++INT_ACTIVATE_START++# in the same cycle, since the forced [.monospaced]#++DISABLED++# meets pending traffic; the handler above answers both. The sequences of xref:aou-737-fdi-link-lifecycle-sequences[Section 7.3.7] show each case.
The same applies to any FDI LinkError, whether AOU_CORE requested it or the D2D adapter entered it on its own: a LinkError can interrupt a flit in either direction, and AOU_CORE's FDI data paths keep that flit's position until [.monospaced]#++AOU_SW_RESET++#. On [.monospaced]#++AOU_TOP++# the FDI bringup controller therefore holds the link down after a LinkError ([.monospaced]#++O_FDI_FSM_STATE++# reads LinkError, [.monospaced]#++O_FDI_LINK_UP++# is 0) until SW has written [.monospaced]#++AOU_SW_RESET++#; SW then reprograms the configuration registers, restarts the link on the UCIe controller, and re-activates AOU once [.monospaced]#++O_FDI_LINK_UP++# is back (xref:{aou-integration-xref}#aou-ig-supported-state-transitions[Integration guide Section 6.6.3]).
Restarting the link after a LinkError, LinkReset or Disabled is SW's job on the UCIe controller (the D2D adapter's Start UCIe Link Training, or the remote die): the AOU bringup controller requests nothing in those states, drives NOP, follows the D2D adapter to Reset and waits for [.monospaced]#++pl_inband_pres++# as after a cold reset.
Asserting [.monospaced]#++I_RESETN++# returns the configuration registers to the same reset values as [.monospaced]#++AOU_SW_RESET++#, and on [.monospaced]#++AOU_TOP++# it also returns the FDI bringup controller to Reset (xref:{aou-integration-xref}#aou-ig-reset-domains[Section 3.1.1]).

[[aou-737-fdi-link-lifecycle-sequences]]
==== 7.3.7. FDI link lifecycle sequences

The sequences below show, for each way the FDI link comes up, goes down or pauses, what the FDI bringup controller of [.monospaced]#++AOU_TOP++# does on its own, what AOU_CORE does, and what is left to SW on the configuration registers or on the UCIe controller. Participants are SW, AOU_CORE, the bringup controller ([.monospaced]#++AOU_FDI_BRINGUP_CTRL++#), the D2D adapter and the remote die. UCIe state encodings are those of [.monospaced]#++pl_state_sts++# (UCIe r1.1 section 8.2.7); [.monospaced]#++O_FDI_FSM_STATE++# reports the same code (xref:{aou-integration-xref}#aou-ig-fdi-bringup-flow-aou_top-only[Integration guide Section 6.6]).

*Bring-up.* The link comes up once the D2D adapter reports presence and either side asks for it. On the local side the bringup controller raises [.monospaced]#++lp_wake_req++# and requests Active on [.monospaced]#++I_SW_ACTIVATE_START++# (a top-level pulse) or on [.monospaced]#++INT_ACTIVATE_START++# (AOU_CORE has a pending local AXI transaction or a received ActivateReq and [.monospaced]#++ACTIVATE_START++# is 0); the D2D adapter asks with [.monospaced]#++pl_clk_req++#. Writing [.monospaced]#++ACTIVATE_START++# alone does not wake the link. [.monospaced]#++I_INT_FSM_IN_ACTIVE++# rises on Active and the activation handshake of xref:aou-732-activation-start[Section 7.3.2] follows; an [.monospaced]#++ACTIVATE_START++# written earlier proceeds then.

image::fdi-seq-02-bringup-clk-req.svg[Bring-up requested by the D2D adapter (pl_clk_req), remote die activates first]

*Deactivation.* Deactivation is an AoU message exchange only: the link stays Active, the bringup controller does nothing, and SW does nothing on the UCIe controller. A remote DeactivateReq reaches SW as [.monospaced]#++INT_DEACTIVATE_START++#; SW answers by writing [.monospaced]#++DEACTIVATE_START++# (xref:aou-733-deactivation-start[Section 7.3.3]).

image::fdi-seq-03-deactivate-local.svg[Deactivation started by SW]

image::fdi-seq-04-deactivate-remote.svg[Deactivation started by the remote die]

*Link down with AoU DISABLED.* The PM entry and LinkDisable sequences of xref:aou-736-pm-entry--linkreset--linkdisabled-sequence[Section 7.3.6] deactivate AoU first. The bringup controller follows the adapter to LINKDOWN and then RESET, drives NOP and requests nothing; [.monospaced]#++I_INT_FSM_IN_ACTIVE++# falls with the activation FSM already DISABLED and no ActivateReq outstanding, so no [.monospaced]#++INT_FDI_LINK_DOWN++# is raised. An [.monospaced]#++ACTIVATE_START++# written while the link is down waits in AOU_CORE until SW restarts the link on the UCIe controller.

image::fdi-seq-05-sw-link-disable.svg[Link Disable by SW with AoU deactivated, then restart]

*Link down with AoU in use.* When the adapter or the remote die takes the link down (LinkReset, Disabled, or a LinkError the adapter entered on its own) while the activation FSM is in ACTIVATE, ENABLED or DEACTIVATE (or in DISABLED with an ActivateReq already sent or received), [.monospaced]#++I_INT_FSM_IN_ACTIVE++# falls, the activation FSM returns to DISABLED, [.monospaced]#++AOU_INIT.INT_FDI_LINK_DOWN++# is set and [.monospaced]#++INT_FDI_LINK_DOWN++# is raised unless masked (xref:aou-4-interrupt[Section 4]). SW runs the LinkReset sequence of Section 7.3.6. After a LinkError the bringup controller also holds the link down until [.monospaced]#++AOU_SW_RESET++# has been written.

image::fdi-seq-06-linkreset-in-use.svg[LinkReset by the D2D adapter or remote die with AoU ENABLED]

image::fdi-seq-08-adapter-linkerror.svg[LinkError entered by the D2D adapter with AoU ENABLED]

*LinkError requested by AOU_CORE.* An activation, deactivation or MsgCredit timeout, or an out-of-step activation message, returns the activation FSM to DISABLED, raises [.monospaced]#++INT_REQ_LINKRESET++# and asserts [.monospaced]#++O_AOU_REQ_LINKRESET++#; the bringup controller pulses [.monospaced]#++lp_linkerror++# (xref:aou-723-linkreset-error-reporting[Section 7.2.3]). The FSM is already DISABLED when the link goes down, so [.monospaced]#++INT_FDI_LINK_DOWN++# is not raised as well. The bringup controller takes the request in ACTIVE and RETRAIN only; raised in L1 or during the L1 exit (an Ack time-out on an [.monospaced]#++ACTIVATE_START++# written in L1), it is held on the sticky status bit and acted on once the link is Active, so SW exits L1 on the UCIe controller before clearing the status (xref:aou-723-linkreset-error-reporting[Section 7.2.3]).

image::fdi-seq-07-aou-linkerror.svg[LinkError requested by AOU_CORE on an AoU error]

*Retrain and L1.* Both are transparent to AOU_CORE: [.monospaced]#++I_INT_FSM_IN_ACTIVE++# stays asserted, the activation FSM keeps its state and no interrupt is raised; only [.monospaced]#++O_FDI_LINK_UP++# drops while the link is not in Active. The bringup controller re-requests Active after a Retrain. From L1 it wakes the link when the adapter raises [.monospaced]#++pl_clk_req++# (the PM exit SW requests on the UCIe controller, or the remote die's) or when AOU_CORE raises [.monospaced]#++INT_ACTIVATE_START++# (local traffic arrives while AoU is DISABLED). An [.monospaced]#++ACTIVATE_START++# written in L1 wakes nothing: the handshake starts at once, its ActivateReq waits in the TX path until the link is Active again, and the Ack timer runs meanwhile, so SW exits L1 on the UCIe controller within the Ack time-out or handles the resulting ACT_ACK_ERR as any other; the time-out is the intended report, not a hazard the hardware avoids.
